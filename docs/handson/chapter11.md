# 第11章 ハンズオン: ループエンジニアリング(ノック101〜107)

> この章の前に [loop-engineering.md](loop-engineering.md)(概念と、100本全体の再整理)を読むこと。

第1〜10章は「エージェントの部品」を1つずつ扱ってきた。この章は視点を変えて、
**エージェントの外側のループ(ハーネス)そのものを設計対象にする**。
プロンプトエンジニアリングが1回の呼び出しの質なら、ループエンジニアリングは
「何周回すか・いつ止めるか・各周で何を戻すか」の工学だ。

7本すべて **AWS 不要**(MockModel で動く)。ループ制御は「モデルの中身」ではなく
「回し方」の話なので、応答を台本化できる MockModel と相性が抜群にいい。

## ループ設計の3原則(この章の背骨)

1. **有界であれ** — あらゆるループに止まる保証を付ける(102・103・107)
2. **各周を意味あるものに** — 1周ごとに前進しているか(104・105・106)
3. **止まり方を設計せよ** — なぜ止まったかを区別し、その後を決める(101)

## ノック101: ループの解剖

📄 `knocks/k101_loop_anatomy.py`

`stop_reason` でループの止まり方を全分類する。

| stop_reason | 意味 | 止めたのは |
|---|---|---|
| `end_turn` | モデルがタスク完了と判断 | モデル(自然終了)|
| `max_tokens` | 1回の出力が頭打ち | モデル設定 |
| `tool_use` | ツールを呼ぶため一旦停止 | ループは継続 |
| `limit_turns` | 反復回数の上限(ノック102) | **ハーネス** |
| `limit_total_tokens` | トークン予算の上限(ノック103) | **ハーネス** |

**観察ポイント**

- `end_turn`(タスクが終わった)と `limit_*`(ハーネスが止めた)は**意味が全く違う**。
  前者は成果、後者は「途中で打ち切った」。この区別が、止まった後の行動
  (再開する? 報告する? 人間に聞く?)を決める
- 第1章 ノック10 の `stop_reason` を「ループ制御の信号」として捉え直す章の入口

## ノック102: 反復回数で縛る

📄 `knocks/k102_bounded_turns.py`

```python
result = agent("すべての結果を集めて", limits=Limits(turns=3))
# result.stop_reason == "limit_turns"
```

**観察ポイント**

- ツールを使うエージェントは条件次第で延々ループする(検索→検索→…)。
  `Limits(turns=N)` で N 周で確実に止める = **第1原則「有界であれ」の最も直接的な実装**
- **上限で止まっても `agent.messages` は再開可能**。だから「まず3周 → 様子を見て → もう2周」の
  分割実行ができる(ノック102 はこれを実演)
- `turns` は1呼び出しごとにリセット(累計ではない)。`metrics.cycle_count` は agent 生涯の累計、
  という違いに注意

## ノック103: トークン予算で縛る

📄 `knocks/k103_bounded_budget.py`

```python
result = agent("全部集めて", limits=Limits(total_tokens=50))
# result.stop_reason == "limit_total_tokens"
```

**観察ポイント**

- 回数(102)ではなく**使ったトークンの合計**で止める。1周が重いエージェント
  (長い履歴 + 大きなツール結果)は、回数が少なくてもコストが膨らむ
- **ソフトキャップ**: 1回のモデル呼び出しの途中では止まらず、周の境界でチェックするので
  多少オーバーする。「厳密な上限」ではなく「概ねこの辺で止める」
- 第8章 ノック79 のコスト換算と組み合わせれば「1リクエスト $0.05 まで」を
  トークン上限に翻訳して実装できる

## ノック104: 自己修正ループ(Reflexion)

📄 `knocks/k104_reflexion_loop.py`

```
生成 → 自己批評(critic)→ 批評を戻して改稿 → 合格 or 上限まで
```

**観察ポイント**

- **「再試行」と「自己修正」は違う**。ただ同じ入力で再実行しても前進しない。
  Reflexion は**批評を次の入力に戻す**から1周ごとに良くなる(第2原則「各周を意味あるものに」)
- critic は第8章 ノック76 の LLM-as-a-Judge の応用。worker と critic を別エージェントにする
- **必ず `max_rounds` で有界化**。批評が延々と不合格を出す事故を防ぐ(第1原則との合わせ技)
- テストでは「合格したら止まる」と「永遠に不合格でも上限で止まる」の両方を検証

## ノック105: 検証ループ(loop-until-verified)

📄 `knocks/k105_verify_loop.py`

Reflexion(104)の批評役を、LLM ではなく**機械的なチェッカ**にする。

```python
loop_until_verified("JSON を作って", generator,
                    lambda t: verify_json(t, {"name", "age"}), max_attempts=4)
```

**観察ポイント**

- テスト実行・スキーマ検証・正規表現・コンパイル — 客観的に合否が出るものが相手なら、
  自己採点(104)より**確実**。「エラー詳細を戻して直させる」を通るまで繰り返す
- **これはエージェンティックなコーディングの心臓部そのもの**:
  コード生成 → テスト実行 → 落ちたらエラーを見せて修正 → 通るまで(有界に)
- 成功でも失敗でも必ず有界に止まる。通らないタスクで無限に回らない
- テストでは3回目で通過するケースと、上限で諦めるケースの両方を検証

## ノック106: 予算駆動ループ

📄 `knocks/k106_budget_driven_loop.py`

```python
while budget.remaining() >= per_round_estimate:
    ideas.append(agent("次のアイデアを1つ"))
    budget.charge(...)
```

**観察ポイント**

- 102・103 は「上限で止める」防御。予算駆動ループは、その予算を
  **「どこまで頑張るか」の積極的な設計変数**として使う
- 同じコードでも予算を増やすと成果が深くなる(予算30→2案、75→5案)。
  Claude の /loop や深掘り系エージェントの基本骨格
- 「予算が事故防止の上限であると同時に、成果の深さを決めるツマミでもある」という二面性

## ノック107: 暴走ガード

📄 `knocks/k107_runaway_guard.py`

`Limits`(102・103)は外側の絶対上限。だが上限内でも「同じツールを同じ引数で
何度も呼ぶ」空回りは起きる。これを**回数上限より早く**検知して止める。

```python
class RepetitionGuard(HookProvider):
    def check(self, event: BeforeToolCallEvent):
        fingerprint = event.tool_use["name"] + json.dumps(event.tool_use["input"], sort_keys=True)
        if self.counts[fingerprint] > self.threshold:
            event.cancel_tool = "同じ操作を繰り返しています。別の方法を試して"
```

**観察ポイント**

- 第5章のフック(ノック46)の応用。呼び出しの「指紋」(ツール名+引数)を数えて、
  閾値超えでキャンセル → モデルは「別の手を試すか諦める」
- **有界(102)と前進しているか(107)は別の安全網**。外側=回数/予算の絶対上限、
  内側=空回りの早期検出。この二重化が定石
- テストでは「同一呼び出しは3回目で止まる」「引数が違えば止まらない」の両方を検証

## この章のテスト

`tests/test_chapter11.py`(全部 AWS 不要、13テスト、累計 81 passed)。見どころ:

- **有界性の証明** — 「合格したら止まる」だけでなく「永遠に合格しなくても上限で止まる」を
  必ずペアで検証(Reflexion・検証ループ)。第1原則がコードで保証されていることのテスト
- **前進の証明** — 予算を増やすと成果が増える(2案→5案)、検証ループが retry のたびに
  エラーが変わって最終的に通る、を検証
- **二重の安全網** — 暴走ガードが Limits(turns=10) に達する前に反復を止めることを検証

## 第11章のまとめ

- エージェント = 外側のループ。その設計が「ループエンジニアリング」
- **有界であれ**: `Limits(turns=/total_tokens=)`(102・103)+ 暴走ガード(107)
- **各周を意味あるものに**: Reflexion(104)/ 検証ループ(105)/ 予算駆動(106)
- **止まり方を設計せよ**: `stop_reason` で「成果」と「打ち切り」を区別(101)
- 外側=絶対上限、内側=空回り検出の**二重の安全網**を掛ける
- ループ制御は MockModel と好相性 — 「回し方」を決定的にテストできる

そして [loop-engineering.md](loop-engineering.md) に戻ると、第1〜10章のすべてが
「ループのどこかを制御する話だった」と見えてくる。100本は、巨大な1つのループの
各パーツを組み立てる旅だった。
