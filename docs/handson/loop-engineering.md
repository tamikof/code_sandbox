# ループエンジニアリング — 100本ノックを貫く背骨

## ループエンジニアリングとは

**プロンプトエンジニアリング**が「1回のモデル呼び出しの質」を上げる技術なら、
**ループエンジニアリング**は「モデルを繰り返し呼ぶ外側のループ(ハーネス)」を設計する技術。

エージェントの正体は、突き詰めると次のループだ:

```
観察(observe) → 思考/生成(think) → 行動(act) → 結果を観察(observe) → ...
```

このループについて、エンジニアが決めるべきことは多い:

- **各周でコンテキストに何を戻すか**(履歴全部? 要約? ツール結果だけ?)
- **いつ止めるか**(タスク完了? 回数上限? 予算切れ? 品質基準を満たしたら?)
- **どう暴走を防ぐか**(無限ループ・同じ失敗の繰り返し)
- **失敗からどう回復するか**(再試行? 別の手? 人間に聞く?)
- **品質をどう担保するか**(自己批評ループ? 外部検証ループ?)

Strands はこのループ(event loop)を実装として持っている。第1章で見た `cycle_count` は
「ループが何周したか」であり、`stop_reason` は「ループがなぜ止まったか」だ。
**この2つを意識した瞬間から、あなたはループエンジニアリングを始めている。**

## 第11章で「新しく」学ぶこと

上の表で **第11章** とあるものが、ループエンジニアリングに特化した新しい演習(ノック101〜107)。
既存の100本が「ループの各部品」を扱ってきたのに対し、第11章は
**ループそのものを設計対象として正面から扱う**:

| No | タイトル | パターン |
|---|---|---|
| 101 | ループの解剖 | `stop_reason` の全分類でループの止まり方を理解する |
| 102 | 反復回数で縛る | `Limits(turns=)` で暴走を有界化し、続きから再開する |
| 103 | トークン予算で縛る | `Limits(total_tokens=)` でコストを上限で止める |
| 104 | 自己修正ループ(Reflexion) | 生成 → 自己批評 → 改稿を、合格または上限まで |
| 105 | 検証ループ(loop-until-verified) | 出力を外部チェッカにかけ、通るまで有界に再試行 |
| 106 | 予算駆動ループ | コスト上限に達するまで探索を続ける(深さを予算で決める) |
| 107 | 暴走ガード | 無限ループ・同一アクション反復を検出して止める |

すべて MockModel で動くので **AWS 認証情報なしでテストまで完結**する。
ループ制御は「モデルが何をするか」ではなく「ハーネスがどう回すか」の話なので、
モデルを台本化できる MockModel と相性が抜群にいい。

## ループ設計の3原則(第11章の通奏低音)

1. **有界であれ(Bounded)** — あらゆるループには止まる保証を付ける。
   回数・予算・時間・品質基準 — 何であれ「無限に回りうる」状態を残さない(ノック102・103・107)。

2. **各周を意味あるものに(Progressive)** — ループが1周するたびに状態が前進しているか?
   同じ入力で同じ失敗を繰り返すループは、有界でも無駄。前進の指標(検証・採点・予算消費)を
   ループの中に埋め込む(ノック104・105・106)。

3. **止まり方を設計せよ(Explicit termination)** — なぜ止まったかを `stop_reason` で区別し、
   止まった後にどうするか(再開・報告・人間へ)を決めておく(ノック101)。

---

これらを読んでから第11章のノックに進むと、
「なぜこのループにこの上限を付けるのか」が腹落ちするはずだ。
そして第1〜10章を読み返すと、**すべてが「ループのどこかを制御する話」だった**ことに気づく。
