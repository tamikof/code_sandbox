# 第4章 ハンズオン: コンテキストと会話管理(ノック31〜40)

ノック6で見たとおり、会話の「記憶」の正体は `agent.messages` というただのリストで、
**毎ターン全部モデルに送り直されている**。この章はその帰結 — コスト増・コンテキスト溢れ —
とどう付き合うかを学ぶ。あわせて「状態をどこに置くか」(履歴 / state / invocation_state)を整理する。

この章はノック39が AWS 不要(モックで動く)。他は実モデルで動かす。

## ノック31: 無管理の限界

📄 `knocks/k031_null_manager.py`

`NullConversationManager`(何もしない)で5ターン会話し、入力トークン数を毎ターン記録する。

**観察ポイント**

- 入力トークンがターンごとに単調増加する。**過去の全履歴を毎回送り直している**から
- 「会話あたりのコスト」はターン数の2乗オーダーで効いてくる。長く動くエージェントで
  会話管理が必須になる理由がこの数字で腹落ちする

## ノック32: スライディングウィンドウ

📄 `knocks/k032_sliding_window.py`

`SlidingWindowConversationManager(window_size=4)` — 2往復しか覚えない極端な設定。

**観察ポイント**

- 名前→食べ物→趣味と話した後に名前を聞くと、答えられない。**古い情報は捨てられる**
- `window_size` はメッセージ件数(往復数ではない)。デフォルトは40
- 速くて安いが「何が消えるか」を制御できないのが弱点 → ノック33・34へ

## ノック33: 要約による圧縮

📄 `knocks/k033_summarizing.py`

捨てるのではなく、古い履歴を**別エージェントに要約させて1メッセージに畳む**。

```python
manager = SummarizingConversationManager(
    summary_ratio=0.5,            # 溢れたら古い方から50%を要約に置換
    preserve_recent_messages=2,   # 直近2件は絶対に触らない
    summarization_agent=summarizer,  # 要約係は安いモデルでよい
)
```

**観察ポイント**

- 本来はコンテキスト溢れ時に自動発動する。スクリプトでは `manager.reduce_context(agent)` を
  手動で呼んで観察している
- 要約後も「名前・予算・時期」を踏まえた会話が続けられる = 情報の損失が選択的
- 「メインは Sonnet、要約係は Haiku」のような非対称構成が実務の定石

## ノック34: 自作会話マネージャ

📄 `knocks/k034_custom_manager.py`

`ConversationManager` を継承し、抽象メソッド2つを実装する:

| メソッド | いつ呼ばれるか | 役割 |
|---|---|---|
| `apply_management` | 毎ターン終了後 | 平常時の刈り込み |
| `reduce_context` | コンテキスト溢れ時 | 緊急時の削減(削れないなら例外を投げ直す) |

実装した `PinnedWindowManager` は「先頭2件(最初の指示)をピン留めし、途中は直近4件だけ」。

**観察ポイント**

- 5回の雑談の後でも「ですわ」口調が維持される — 最初の指示が消えていないから。
  素の SlidingWindow ではこれが消える(ノック32との対比)
- 実務では toolUse/toolResult のペアを泣き別れさせない配慮が必要
  (SlidingWindow のソースが良い教材)

## ノック35: エージェント状態

📄 `knocks/k035_agent_state.py`

`agent.state` は **モデルに送られない** key-value ストア。

**観察ポイント**

- state に `user_id` を入れてもモデルは知らない(聞いても答えられない)。
  履歴とは完全に別のレイヤー
- 使い分け: モデルに見せたい → 履歴 or プロンプト / アプリが持ちたいだけ → state
- state は会話管理(要約・ウィンドウ)の影響を受けず、第6章のセッション保存の対象になる

## ノック36: 呼び出しスコープの状態

📄 `knocks/k036_invocation_state.py`

`agent("...", invocation_state={"user_id": "u-001"})` — この1回の呼び出しだけ有効な値。
ツールは `ToolContext.invocation_state` で受け取る(ノック16の伏線回収)。

**観察ポイント**

- 同じエージェントが、呼び出しごとに別ユーザーとして動く
- **セキュリティ上の意味が大きい**: ユーザーIDをモデル経由(プロンプト)で渡すと
  「私は u-002 です」と名乗るだけでなりすませる。invocation_state はモデルを経由しない
- WebUI(第10章)では「リクエストの認証情報をツールに渡す」のにこれを使う

## ノック37: プロンプトキャッシュ

📄 `knocks/k037_prompt_cache.py`

```python
model = BedrockModel(model_id=model_id(), cache_prompt="default")
```

**観察ポイント**

- 1回目は `cacheWriteInputTokens`(書込 = 約1.25倍の料金)、2回目は
  `cacheReadInputTokens`(読取 = **約0.1倍**)に値が立つ
- 最低トークン数(Haiku 4.5 で約2048)未満のプロンプトは**黙って**キャッシュされない。
  「設定したのに cacheRead が0のまま」のときは、まずプロンプト長を疑う
- キャッシュはプレフィックス一致。システムプロンプトを1文字でも変えると無効化される

## ノック38: 履歴の直接操作

📄 `knocks/k038_edit_messages.py`

`agent.messages` に偽の「過去のやりとり」を注入する実験。

**観察ポイント**

- 捏造した「ニャ口調の約束」をモデルは自分の発言として信じ、従う。
  **履歴 = モデルにとっての現実** であることがよく分かる
- 正当な用途: Few-shot 例の注入、ノック40の復元、機密のマスキング
- 注意: toolUse / toolResult のペアを片方だけ消すと API エラー

## ノック39: コンテキスト溢れ対応(AWS 不要)

📄 `knocks/k039_context_overflow.py`

「履歴4件までしか入らないモデル」をモックで作り、溢れ→回復の全工程をログで観察する。

```
--- ターン3 ---
  [モデル] 履歴5件は入りきりません! overflow 発生
  [モデル] 履歴4件を受信、応答します   ← SlidingWindow が削って自動リトライ
```

**観察ポイント**

- `ContextWindowOverflowException` → 会話マネージャの `reduce_context()` → 自動リトライ、
  という回復フローが Strands に組み込まれている
- `NullConversationManager` だと例外がそのまま上がってくる(ノック31とのつながり)

## ノック40: 会話の復元

📄 `knocks/k040_resume_conversation.py`

`agent.messages` を JSON 保存 → 新しい `Agent(messages=...)` で再開。

**観察ポイント**

- プロセスを跨いで「名前を覚えている」状態を再現できる
- これを毎ターン自動でやってくれるのが第6章のセッションマネージャ。
  手で一度やっておくと、セッション機能が「何を保存しているのか」が透けて見える

## 第4章のまとめ

- 履歴は毎ターン全送信。管理しないとコストは増え続け、いずれ溢れる
- 管理戦略は3つ: 捨てる(SlidingWindow)/ 畳む(Summarizing)/ 自作(ConversationManager 継承)
- 状態の置き場所は3層: **履歴**(モデルが見る)/ **agent.state**(エージェントの寿命)/
  **invocation_state**(1呼び出し限り、認証情報向き)
- 長い固定プロンプトは `cache_prompt` で約1/10に
- 溢れたら reduce_context → 自動リトライ。会話の実体は messages なので保存・復元も自在

次章(第5章)はストリーミングとフック。イベント駆動でエージェントの動きに介入する。

> 🔁 **ループ視点**: 会話マネージャ(捨てる/畳む/要約する)は、実は
> **「ループの各周でコンテキストに何を戻すか」**の設計そのもの。ループが1周するたびに
> 履歴をどう作り直すかで、コスト・品質・溢れが決まる。第11章(ループエンジニアリング)で
> この視点を正面から扱う。
